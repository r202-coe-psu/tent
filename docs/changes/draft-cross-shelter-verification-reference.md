# จิตอาสาหลายศูนย์ — แสดงผลยืนยันจากศูนย์อื่นให้เจ้าหน้าที่กดรับ

> **สรุป (TL;DR):**
>
> - **เปลี่ยนอะไร:** หน้า "ตรวจสอบ & อนุมัติ" ของจิตอาสาแสดงผลยืนยันตัวตนและทักษะที่รับรองแล้ว**จากศูนย์อื่น**ที่เบอร์ (และเลขบัตร ถ้ามีทั้งคู่) ตรงกัน พร้อมที่มา เจ้าหน้าที่**กดรับ**ทีละรายการเพื่อบันทึกในศูนย์นี้ — **ไม่มีการรับอัตโนมัติ**
> - **เพื่อใคร / ทำไม:** จิตอาสาที่ไปหลายศูนย์ไม่ต้องกรอกและตรวจหลักฐานซ้ำทั้งหมด แต่ผู้ออกสิทธิ์ในศูนย์ยังเป็นคนตัดสินเอง (สอดคล้อง CR-221 FR-3 "ยืนยันตัวตนในศูนย์นี้")
> - **build:** endpoint อ่านอย่างเดียว `GET /api/v1/volunteers/cross-shelter-verifications` + ส่วนแสดงผลใน dialog + ปุ่ม "ยืนยันตัวตน (อ้างอิงผลจาก SHxxx)" / "รับรองทักษะนี้" ที่เขียนลงโปรไฟล์ของศูนย์นี้ด้วย flow เดิม
> - **schema:** ไม่เปลี่ยน field / `schema_v` · เปลี่ยน decision D-MULTI ของ CR-041 จาก A (โปรไฟล์กลาง) เป็น D (โปรไฟล์ต่อศูนย์ + ใช้ผลจากศูนย์อื่นแบบกดรับ)

---

## Why

- **ปัญหาหน้างาน (#886):** จิตอาสาที่ไปหลายศูนย์ต้องยืนยันตัวตนและทักษะใหม่ทุกศูนย์
- **D-MULTI ใน CR-041 = A (โปรไฟล์กลาง) ไม่ตรงกับโค้ด:** โปรไฟล์เก็บแยกต่อ DB ศูนย์ (stable core: VDU ต่อศูนย์, edge replica, projection) การทำโปรไฟล์กลางแพงและต้องเก็บ PII นอกศูนย์ (@net-lynx, #886)
- **ไม่รับผลยืนยันตัวตนอัตโนมัติ:** CR-221 FR-3 (approved 2026-11-01) กำหนดให้ยืนยันตัวตน**ในศูนย์ที่ออกสิทธิ์**ก่อนออกสิทธิ์ทุกครั้ง ผลจากศูนย์อื่นใช้แทนไม่ได้ ทาง D เดิมของ #886 ("ใช้ต่ออัตโนมัติ") จึงขัดกัน → owner เลือก "แสดงและกดรับ" (2026-11-02)
- **ทักษะ:** มาตรฐานการรับรองแต่ละศูนย์อาจไม่เท่ากัน และบางทักษะผูกกับบริบทศูนย์ จึงต้องกดรับ (ตามคำตอบเดิมของ @net-lynx)

## Change

### ค้นผลจากศูนย์อื่น

- **FR-1 endpoint:** `GET /api/v1/volunteers/cross-shelter-verifications?shelter_code=&volunteer_id=` (BFF, admin credential ฝั่ง server)
  - ผู้เรียก: SA / SM / `volunteer_coordinator` ของ `shelter_code` (`canAccessVolunteerBackoffice`) อื่น ๆ 403
  - อ่านโปรไฟล์ `volunteer_id` ในศูนย์ที่ขอ แล้วค้นโปรไฟล์ `type: volunteer` ใน DB ของ**ศูนย์อื่นทุกศูนย์**ที่ `phone_hash` ตรงกัน (วิธีเดียวกับ `resolveIdentities` ใน `public-schedule-action.ts`)
  - **FR-2 จับคู่:** นับว่าเป็นคนเดียวกันเมื่อ `phone_hash` ตรง **และ** ถ้าทั้งสองโปรไฟล์มี `national_id_hash` ต้องตรงกันด้วย (มีฝั่งเดียวหรือไม่มีทั้งคู่ = ใช้เบอร์อย่างเดียว); โปรไฟล์ที่ `status: inactive` ไม่นับ
  - โปรไฟล์ไม่มีเบอร์ (walk-in ใช้บัตรแทน #880 / #952) → คืนรายการว่าง
- **FR-3 ข้อมูลที่คืน:** ต่อศูนย์ที่พบ `{ shelter_code, shelter_name, identity: { reviewed_by, reviewed_at } | null, skills: [{ code, reviewed_by, reviewed_at, credential_reference }] }`
  - `identity` มีเฉพาะเมื่อ `identity_verification.status = verified` ในศูนย์นั้น · `skills` เฉพาะ `skill_verifications[code].status = verified`
  - **ไม่คืน** ชื่อ, เบอร์, เลขบัตร, `_id` ของโปรไฟล์ศูนย์อื่น, รหัส V-xxx หรือข้อมูลการพัก/กะ (FR-3 คืนเฉพาะสิ่งที่ใช้ตัดสินการรับ)

### แสดงผลและกดรับ

- **FR-4 ตัวตน:** dialog "ตรวจสอบ & อนุมัติ" (`volunteer-qualification-dialog.svelte`) ของโปรไฟล์ที่ยังไม่ยืนยันในศูนย์นี้ แสดง "ยืนยันตัวตนแล้วที่ <ศูนย์> โดย <reviewed_by> เมื่อ <วันที่>" ต่อศูนย์ที่พบ
  - ปุ่ม "ยืนยันตัวตน (อ้างอิงผลจาก <ศูนย์>)" บันทึก `identity_verification` ของโปรไฟล์**ศูนย์นี้**ด้วย flow ยืนยันเดิม (`status: verified`, `reviewed_by` = ผู้กด, `reviewed_at` = ตอนกด) และ `notes` = "อ้างอิงผลยืนยันจาก <shelter_code> โดย <reviewed_by> เมื่อ <reviewed_at>"
  - **ไม่มีการนับว่ายืนยันแล้วโดยอัตโนมัติ** — จนกว่าจะกดรับ โปรไฟล์ศูนย์นี้ยังเป็น "รอยืนยันตัวตน" และออกสิทธิ์ไม่ได้ (CR-221 FR-3)
- **FR-5 ทักษะ:** ทักษะควบคุมที่โปรไฟล์ศูนย์นี้ระบุไว้แต่ยังไม่รับรอง และรับรองแล้วที่ศูนย์อื่น แสดง "รับรองแล้วที่ <ศูนย์> โดย <reviewed_by> เมื่อ <วันที่>" + ปุ่ม "รับรองทักษะนี้"
  - กดแล้วบันทึก `skill_verifications[code]` ของโปรไฟล์ศูนย์นี้ (`status: verified`, `reviewed_by` = ผู้กด, `credential_reference` = ค่าจากศูนย์ต้นทาง, `notes` = "รับจาก <shelter_code> …") ด้วย flow รับรองทักษะเดิม
  - ทักษะที่โปรไฟล์ศูนย์นี้ไม่ได้ระบุ ไม่แสดง (ไม่เพิ่มทักษะให้)
- **FR-6 ผู้กดรับ:** SA / SM / VC ของศูนย์นี้ (`canAccessVolunteerBackoffice`) — ชุดเดียวกับผู้ที่ยืนยันตัวตน / รับรองทักษะในศูนย์ได้อยู่แล้ว
- **FR-7 ไม่แตะ:** ไม่มีโปรไฟล์กลาง ไม่ย้ายข้อมูล ไม่แตะ stable core ไม่เขียนเอกสารของศูนย์อื่น · ผลของศูนย์อื่นที่ถูกยกเลิกภายหลังไม่ย้อนไปยกเลิกของศูนย์นี้ (แต่ละศูนย์ตัดสินเอง)

### CR-041 (before → after)

| ข้อ | ก่อน | หลัง |
| --- | --- | --- |
| D-MULTI (ข้อ 11) | A — โปรไฟล์กลาง อาสาหนึ่งคนหนึ่งโปรไฟล์ | D — โปรไฟล์ต่อศูนย์ (ตามโค้ดปัจจุบัน) + แสดงผลยืนยันจากศูนย์อื่นที่เบอร์ตรงกันให้เจ้าหน้าที่กดรับ (CR นี้) · บัญชีระบบ 1 บัญชีต่อคนข้ามศูนย์อยู่ใน CR-221 Part B |

## Acceptance

- [ ] โปรไฟล์ใน SH002 ที่เบอร์ตรงกับคนที่ยืนยันตัวตนแล้วใน SH001 → dialog แสดง "ยืนยันตัวตนแล้วที่ SH001 โดย … เมื่อ …" แต่สถานะยังเป็น "รอยืนยันตัวตน" และออกสิทธิ์ไม่ได้
- [ ] กด "ยืนยันตัวตน (อ้างอิงผลจาก SH001)" → โปรไฟล์ SH002 ยืนยันแล้ว `reviewed_by` = ผู้กด และ `notes` อ้างอิง SH001
- [ ] ทักษะควบคุมที่รับรองที่ SH001 และโปรไฟล์ SH002 ระบุไว้ → แสดงพร้อมปุ่มรับ กดแล้ว `skill_verifications` ของ SH002 เป็น verified
- [ ] เลขบัตรของสองโปรไฟล์ไม่ตรงกัน (มีทั้งคู่) → ไม่แสดงผลจากศูนย์นั้น
- [ ] โปรไฟล์ไม่มีเบอร์ → ไม่แสดงส่วนนี้
- [ ] role อื่นเรียก endpoint ได้ 403 · response ไม่มีชื่อ / เบอร์ / เลขบัตร / `_id` ของศูนย์อื่น

## Impact

- **ความเป็นส่วนตัว:** SA / SM / VC ของศูนย์ใหม่รู้ว่าคนนี้เคยยืนยันตัวตนหรือรับรองทักษะที่ศูนย์ใด โดยใคร เมื่อไร — ไม่เห็นข้อมูลส่วนตัวอื่นของศูนย์นั้น
- **ประสิทธิภาพ:** ค้นทุกศูนย์ต่อการเปิด dialog 1 ครั้ง (`_find` ด้วย `phone_hash` ต่อ DB) แบบเดียวกับ `resolveIdentities`
- **ข้อจำกัดที่รู้:** walk-in ที่ไม่มีเบอร์เชื่อมข้ามศูนย์ไม่ได้ · คนที่ใช้เบอร์ร่วมกัน (เช่น ครอบครัว) และไม่มีเลขบัตรทั้งคู่อาจแสดงผลของอีกคน — เจ้าหน้าที่ต้องดูบัตรก่อนกดรับ (ไม่รับอัตโนมัติจึงยอมรับได้)
- **CR-221:** ไม่เปลี่ยน FR-3 (ยังต้องยืนยันในศูนย์นี้ก่อนออกสิทธิ์)

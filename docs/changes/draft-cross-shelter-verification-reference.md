# จิตอาสาหลายศูนย์ — แสดงผลยืนยันจากศูนย์อื่นให้เจ้าหน้าที่กดรับ

> **สรุป (TL;DR):**
>
> - **เปลี่ยนอะไร:** dialog "ตรวจสอบ & อนุมัติ" ของจิตอาสาแสดงว่า "ยืนยันตัวตนแล้วที่ <ศูนย์> เมื่อ <วันที่>" / "รับรองแล้วที่ <ศูนย์> เมื่อ <วันที่>" เมื่อพบโปรไฟล์ศูนย์อื่นที่ `phone_hash` **และ** `national_id_hash` ตรงกันทั้งคู่ เจ้าหน้าที่**กดรับ**ทีละรายการเพื่อบันทึกในศูนย์นี้ — **ไม่มีการรับอัตโนมัติ**
> - **เพื่อใคร / ทำไม:** จิตอาสาที่ไปหลายศูนย์ไม่ต้องกรอกและตรวจหลักฐานซ้ำทั้งหมด แต่ผู้ออกสิทธิ์ในศูนย์ยังตรวจบัตรและตัดสินเอง (สอดคล้อง CR-221 FR-3)
> - **build:** endpoint อ่านอย่างเดียว `GET /api/v1/volunteer-access/cross-shelter-verifications` (admin credential ฝั่ง server, คืนเฉพาะ `shelter_code`, `shelter_name`, วันที่ยืนยัน และรหัสทักษะที่ผ่านการกรอง — ไม่คืนชื่อเจ้าหน้าที่ผู้ยืนยัน ไม่คืน `credential_reference`) + ส่วนแสดงผลและปุ่มรับใน dialog ที่เขียนลงโปรไฟล์ของศูนย์นี้ด้วย flow เดิม
> - **schema / layer:** ไม่เปลี่ยน field / `schema_v` · `layer: stable` (อ่านข้ามทุก `shelter_*` ด้วย admin credential = auth / stable core ตาม change-management §1) → **ต้อง review ก่อน approve** · เปลี่ยน decision D-MULTI ของ CR-041 จาก A เป็น D

---

## Why

- **ปัญหาหน้างาน (#886):** จิตอาสาที่ไปหลายศูนย์ต้องยืนยันตัวตนและทักษะใหม่ทุกศูนย์
- **D-MULTI = A / D คืออะไร:** A = โปรไฟล์กลางใบเดียวใช้ได้ทุกศูนย์ (ที่ CR-041 ล็อกไว้ 2026-07-22) · D = คงโปรไฟล์ต่อศูนย์ตามโค้ดปัจจุบัน แต่ใช้ผลยืนยันจากศูนย์อื่นที่เป็นคนเดียวกัน (ตามคำตอบของ @net-lynx ใน #886)
- **A ไม่ตรงกับโค้ด:** โปรไฟล์เก็บแยกต่อ DB ศูนย์ (stable core: VDU ต่อศูนย์, edge replica, projection) โปรไฟล์กลางแพงและต้องเก็บ PII นอกศูนย์ (@net-lynx, #886)
- **ไม่รับผลยืนยันตัวตนอัตโนมัติ:** CR-221 FR-3 (approved 2026-11-01) กำหนดให้ยืนยันตัวตน**ในศูนย์ที่ออกสิทธิ์**ก่อนออกสิทธิ์ทุกครั้ง ผลจากศูนย์อื่นใช้แทนไม่ได้ ทาง D เดิมของ #886 ("ใช้ต่ออัตโนมัติ") จึงขัดกัน → owner เลือก "แสดงและกดรับ" (#886, 2026-11-02)
- **จับคู่ด้วยเบอร์ + เลขบัตรทั้งคู่:** เป็นกฎเดียวกับ CR-213 FR-3(ข) / AC-3 และ CR-221 FR-30 เพื่อไม่ให้ผลยืนยันของคนหนึ่งไปปรากฏที่โปรไฟล์ของอีกคนที่ใช้เบอร์ร่วมกัน (owner 2026-11-03)
- **ข้อมูลข้ามศูนย์น้อยที่สุด:** เปิดเผยแค่ว่าเคยยืนยัน/รับรองที่ศูนย์ใดเมื่อไร ไม่เปิดชื่อเจ้าหน้าที่ของศูนย์อื่นและไม่ส่งเลขใบอนุญาต (owner 2026-11-03)
- **ทักษะ:** มาตรฐานการรับรองแต่ละศูนย์อาจไม่เท่ากัน และบางทักษะผูกกับบริบทศูนย์ จึงต้องกดรับ (ตามคำตอบเดิมของ @net-lynx)
- **`layer: stable`:** endpoint ใหม่อ่าน `shelter_*` ของทุกศูนย์ด้วย admin credential (เรื่อง auth / data-plane boundary) ซึ่ง CR-213 ที่ใช้รูปแบบเดียวกันก็เป็น `stable`

## Change

### ค้นผลจากศูนย์อื่น (server)

- **FR-1 endpoint:** `GET /api/v1/volunteer-access/cross-shelter-verifications?shelter_code=&volunteer_id=` (BFF; prefix เดียวกับ endpoint จิตอาสาอื่น)
  - ผู้เรียก: `system_admin` / `shelter_manager` / `volunteer_coordinator` ของ `shelter_code` (`canAccessVolunteerBackoffice`) · อื่น ๆ 403 · ไม่ระบุ `shelter_code` หรือ `volunteer_id` = 422
- **FR-2 ที่มาของข้อมูล:** server ใช้ **admin credential** (`adminRaw`) อ่านโปรไฟล์ `volunteer_id` ในศูนย์ที่ขอ แล้วไล่ `_find` ใน `shelter_{code}` ของทุกศูนย์ใน `registry` ยกเว้นศูนย์ที่ขอ ด้วย selector `{ type: volunteer, phone_hash, national_id_hash }` (รูปแบบเดียวกับการค้นข้ามศูนย์ของ CR-213 FR-3(ข))
  - ไม่ใช่วิธีเดียวกับ `resolveIdentities` (`public-schedule-action.ts`) ซึ่งใช้ `findAsPublicWriter` ที่เป็น identity สิทธิ์จำกัด · CR นี้ใช้ admin credential เพราะต้องอ่านทุก DB ศูนย์ — จึงเป็น stable core และต้อง review
  - ศูนย์ที่ไม่มี DB (404) ข้าม · อ่านไม่สำเร็จแบบอื่น endpoint ตอบ error (FR-12) ไม่คืนผลบางส่วน
- **FR-3 กฎจับคู่ (เป็นคนเดียวกัน):** โปรไฟล์ศูนย์อื่นนับว่าเป็นคนเดียวกันเมื่อ `phone_hash` **และ** `national_id_hash` ตรงกันทั้งคู่ — ไม่มีการจับคู่ด้วยเบอร์อย่างเดียว
  - โปรไฟล์ศูนย์นี้ไม่มี `phone_hash` หรือไม่มี `national_id_hash` (เช่น walk-in ใช้บัตรแทน #880 / #952) → คืน `matches: []`
  - โปรไฟล์ศูนย์อื่นที่ขาด hash ใดตัวหนึ่ง หรือ `status: inactive` → ไม่นับ
  - โปรไฟล์ศูนย์นี้ที่ `status: inactive` → คืน `matches: []`
- **FR-4 response (ฟิลด์ทั้งหมดที่คืน):** `{ ok: true, matches: [{ shelter_code, shelter_name, identity: { reviewed_at } | null, skills: [{ code, reviewed_at }] }] }` — ไม่มีฟิลด์อื่น
  - ศูนย์ที่ไม่มีทั้ง `identity` และ `skills` ไม่อยู่ใน `matches`
  - `identity` ไม่ใช่ `null` เมื่อโปรไฟล์ต้นทาง `identity_verification.status = verified` **และ** โปรไฟล์ศูนย์นี้ยังไม่เป็น `verified`
  - `reviewed_at` = วันที่ยืนยัน/รับรองที่ศูนย์ต้นทาง (ISO 8601)
- **FR-5 กรอง skill ที่ server:** `skills[]` มีเฉพาะ `code` ที่ครบทั้งสามข้อ (กรองฝั่ง server ไม่ใช่ UI)
  - เป็นทักษะควบคุม (controlled) ตามรายการของศูนย์นี้ (`isControlledSkill` + master `volunteer_skills`)
  - อยู่ใน `skills` ของโปรไฟล์ศูนย์นี้
  - ต้นทาง `skill_verifications[code].status = verified` และศูนย์นี้ยังไม่ `verified` ทักษะนั้น
- **FR-6 ห้ามคืน:** ชื่อ-นามสกุล, เบอร์, เลขบัตร / hash, `_id` / รหัส V-xxx ของโปรไฟล์ศูนย์อื่น, ข้อมูลการพัก / กะ, **`reviewed_by` ของศูนย์อื่น** (ไม่ส่งชื่อเจ้าหน้าที่ข้ามศูนย์), **`credential_reference`** และ `notes` ของศูนย์อื่น

### แสดงผลและกดรับ (UI)

- **FR-7 แสดงตัวตน:** dialog "ตรวจสอบ & อนุมัติ" (`volunteer-qualification-dialog.svelte`) ของโปรไฟล์ที่ยังไม่ยืนยันตัวตนในศูนย์นี้ แสดง "ยืนยันตัวตนแล้วที่ <ศูนย์> เมื่อ <วันที่>" ต่อศูนย์ที่พบ — ไม่แสดงชื่อผู้ยืนยัน
- **FR-8 กดรับตัวตน:** ปุ่ม "ยืนยันตัวตน (อ้างอิงผลจาก <ศูนย์>)" บันทึก `identity_verification` ของโปรไฟล์**ศูนย์นี้**ด้วย flow ยืนยันเดิม (`reviewIdentity`: `status: verified`, `reviewed_by` = ผู้กด, `reviewed_at` = ตอนกด)
  - **ต้องตรวจบัตรก่อนกด:** ข้างปุ่มแสดงข้อความ "ตรวจบัตรประชาชนตัวจริงของจิตอาสาต่อหน้าก่อนกดยืนยัน" — เจ้าหน้าที่ศูนย์ปลายทางต้องตรวจบัตรด้วยตนเองทุกครั้ง ผลจากศูนย์อื่นเป็นเพียงข้อมูลอ้างอิง
  - `notes` = "อ้างอิงผลยืนยันจาก <shelter_code> เมื่อ <วันที่>" เท่านั้น — ไม่มีชื่อผู้ยืนยันของศูนย์อื่น
  - จนกว่าจะกดรับ โปรไฟล์ศูนย์นี้ยังเป็น "รอยืนยันตัวตน" และออกสิทธิ์ไม่ได้ (CR-221 FR-3)
- **FR-9 แสดงทักษะ:** ทักษะที่ endpoint คืนมา (FR-5) แสดง "รับรองแล้วที่ <ศูนย์> เมื่อ <วันที่>" + ปุ่ม "รับรองทักษะนี้" ข้างทักษะนั้น — ทักษะที่โปรไฟล์ศูนย์นี้ไม่ได้ระบุไม่แสดงและ CR นี้ไม่เพิ่มทักษะให้
- **FR-10 กดรับทักษะ:** กดแล้วบันทึก `skill_verifications[code]` ของโปรไฟล์ศูนย์นี้ด้วย flow รับรองทักษะเดิม (`reviewSkill`: `status: verified`, `reviewed_by` = ผู้กด, `reviewed_at` = ตอนกด)
  - `credential_reference` **ไม่คัดลอก**จากศูนย์ต้นทาง — เป็นค่าที่เจ้าหน้าที่ศูนย์นี้กรอกเองในช่องเดิมของ dialog (เว้นว่างได้ตามกติกาเดิม)
  - `notes` = "อ้างอิงผลรับรองจาก <shelter_code> เมื่อ <วันที่>" เท่านั้น
- **FR-11 ผู้ใช้งาน (กติกาใหม่):** ส่วนแสดงผลจากศูนย์อื่นและปุ่มรับแสดงเฉพาะ SA / SM / VC ของศูนย์นี้ (`canAccessVolunteerBackoffice`) · endpoint บังคับชุดเดียวกัน (FR-1)
  - `reviewIdentity` / `reviewSkill` (`volunteer.remote.ts`) ไม่มี capability check ในตัวเอง — CR นี้ไม่เพิ่ม (ดูคำถามเปิด Q1)
- **FR-12 เมื่อค้นไม่สำเร็จ:** endpoint อ่านศูนย์ใดไม่สำเร็จ (นอกจาก 404) ตอบ 502 ไม่คืนผลบางส่วน · dialog แสดง toast ผิดพลาดและซ่อนส่วนผลจากศูนย์อื่น · การยืนยันตัวตน / รับรองทักษะด้วยมือใน dialog ยังใช้ได้ตามปกติ
- **FR-13 กรณีขอบ:**
  - หลายศูนย์พบพร้อมกัน → แสดงแยกบรรทัดต่อศูนย์ ไม่รวมผล · กดรับจากศูนย์ใดก็ได้
  - โปรไฟล์ศูนย์นี้ยืนยันตัวตนแล้ว → ไม่แสดงส่วนตัวตน · ทักษะที่ `verified` แล้วไม่แสดง
  - ผลของศูนย์ต้นทางที่ถูกยกเลิก / เปลี่ยนภายหลังไม่ย้อนมายกเลิกของศูนย์นี้ (แต่ละศูนย์ตัดสินเอง)
- **FR-14 ไม่แตะ:** ไม่มีโปรไฟล์กลาง ไม่ย้ายข้อมูล ไม่เขียนเอกสารของศูนย์อื่น ไม่เปลี่ยน `schema_v`

## คำถามที่รอเจ้าของตัดสิน

ตัดสินแล้ว (owner 2026-11-03) และบันทึกใน Change ข้างต้น: จับคู่ด้วย hash ทั้งสอง (FR-3) · ไม่ส่งชื่อผู้ยืนยันข้ามศูนย์ (FR-4, FR-6, FR-7) · ไม่ส่ง / ไม่คัดลอก `credential_reference` (FR-6, FR-10) · กรอง skill ที่ server (FR-5) · `layer: stable` · ต้องตรวจบัตรก่อนกด (FR-8)

ยังเปิดอยู่:

- **Q1 สิทธิ์ที่ชั้นเขียน:** `reviewIdentity` / `reviewSkill` ยังไม่มี capability check — จะให้ CR นี้เพิ่มการบังคับที่ชั้นเขียน (นอกเหนือจากซ่อนปุ่ม + endpoint 403) หรือไม่ · ข้อเสนอ: ไม่เพิ่มใน CR นี้ แยกเป็น issue ต่างหาก เพราะกระทบทุกจุดที่เรียก flow เดิม
- **Q2 โปรไฟล์ศูนย์นี้ `rejected`:** FR-4 คืน `identity` เมื่อศูนย์นี้ "ยังไม่ `verified`" ซึ่งรวมกรณีที่เจ้าหน้าที่ศูนย์นี้ปฏิเสธไปแล้ว · ข้อเสนอ: ไม่แสดงเมื่อศูนย์นี้ `rejected` (การตัดสินของศูนย์นี้ชนะ) — รอยืนยัน
- **Q3 ประสิทธิภาพ:** ค้นขนานทุกศูนย์ต่อการเปิด dialog 1 ครั้ง (`_find` 1 ครั้งต่อ DB, `fields` จำกัด, `limit` ต่ำ) · ยังไม่ระบุจำนวนศูนย์สูงสุดและเป้าเวลาตอบสนอง · ข้อเสนอ: ตั้งเป้า p95 ≤ 2 วินาทีที่จำนวนศูนย์ที่ใช้งานจริงสูงสุด — ต้องให้ owner ระบุตัวเลข

## Impact

- **ความเป็นส่วนตัว:** SA / SM / VC ของศูนย์ใหม่รู้ว่าคนนี้เคยยืนยันตัวตน / รับรองทักษะที่ศูนย์ใดเมื่อไร — ไม่เห็นชื่อเจ้าหน้าที่ ข้อมูลส่วนตัว หรือเลขใบอนุญาตของศูนย์นั้น และการจับคู่ต้องมีทั้งเบอร์และเลขบัตร
- **ความปลอดภัย:** endpoint ใหม่ใช้ admin credential อ่านทุก `shelter_*` (server-only, อ่านอย่างเดียว) — ต้องผ่าน review (stable core) และกรอง response ที่ server (FR-5, FR-6)
- **ประสิทธิภาพ:** ค้นทุกศูนย์ใน `registry` ต่อการเปิด dialog 1 ครั้ง (ดู Q3)
- **ข้อจำกัดที่รู้:** walk-in ที่ไม่มีเบอร์หรือเลขบัตรเชื่อมข้ามศูนย์ไม่ได้ · ผลที่ไม่ตรงกันข้ามศูนย์แสดงแยกบรรทัดให้เจ้าหน้าที่ตัดสิน
- **CR-221:** ไม่เปลี่ยน FR-3 (ยังต้องยืนยันในศูนย์นี้ก่อนออกสิทธิ์) · กฎจับคู่เดียวกับ CR-213 FR-3(ข) / CR-221 FR-30

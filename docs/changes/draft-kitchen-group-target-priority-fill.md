# จัดสรรจานตามกลุ่มเป้าหมายแบบ priority-fill แทนการนับซ้ำข้ามแท็ก

> **สรุป (TL;DR):** ตารางเป้าหมาย 5 กลุ่มในหน้าครัวกลางนับจานซ้ำข้ามแท็ก, ขึ้น "ครบแล้ว" ให้กลุ่มที่
> เป้า 0 และเทียบหน่วยคน/จานปนกัน · เสนอกติกาใหม่: จัดสรรจานแบบ **priority fill** (กลุ่มที่มีข้อจำกัด
> ก่อน) · เป็น derived display logic ล้วน — **ไม่เปลี่ยน persisted shape, ไม่ bump `schema_v`** ·
> มี **open question 2 ข้อ** (Q1–Q2) และ **ข้อเสนอที่รอยืนยัน 4 ข้อ** (D1–D4) ที่ issue ไม่ได้ระบุ

Source: https://github.com/r202-coe-psu/tent/issues/770

## Why

ตาราง "เป้าหมาย 5 กลุ่มความต้องการ" ในหน้าครัวกลางและอาหาร (`MealSessionList`) แสดงตัวเลขที่ทำให้
เข้าใจผิด:

1. **นับซ้ำ** — `computeSessionGroupProgress` บวกยอดผลิตของเมนู (`actual_yield`, หรือ `served`
   ถ้ายังไม่บันทึก `actual_yield`) เต็มจำนวนให้ทุกแท็กของเมนู
2. **กลุ่มเป้า 0 ขึ้น "ครบแล้ว"** — `0 >= 0` และถูกนับเข้าตัวหาร "5/5 กลุ่มครบ"
3. **หน่วยปนกัน** — หัวข้อเขียน "รวม N จาน" แต่ค่าคือ `target_headcount.total` (คน); ตารางเทียบ
   "คน" กับ "จาน" และไม่มีส่วนต่าง (ขาด/เกิน)
4. **ป้ายสรุป "5/5 กลุ่มครบ" เชื่อถือไม่ได้** เพราะข้อ 1–2

ตัวอย่างที่เจอ (มื้อกลางวัน 2026-10-22): เมนูเดียว "ข้าวไข่เจียว" แท็กฮาลาล+ทั่วไป ผลิต 282 จาน
(เป้า ฮาลาล 47, ทั่วไป 235, กลุ่มอื่น 0) → ตารางแสดงฮาลาล 282 และทั่วไป 282 (ดูเหมือนทำ 564 จาน)
และทั้ง 5 กลุ่มขึ้น "ครบแล้ว"

การแก้ไม่ใช่แค่ bugfix การแสดงผล — ต้องกำหนด **กติกาการจัดสรรจานให้แต่ละกลุ่มเมื่อเมนูหนึ่งครอบคลุม
หลายกลุ่ม** ซึ่งเป็น business rule ที่ยังไม่เคยบันทึกไว้ใน `docs/` (ไม่มี spec ของ `meal_session` /
`target_tags` / `target_headcount` ใน `docs/data/` หรือ `docs/features/`) จึงต้องขอ sign-off ตาม
`docs/change-management.md` §2 (เปลี่ยน business rule/invariant)

spec ที่เกี่ยวข้องและมีอยู่แล้วมีข้อเดียว: `docs/data/schema.md` หัวข้อ "Headcount source — occupancy
mapping (CR-022)" ของ `meal_plan.headcount` ระบุว่ากลุ่มย่อย (`halal`, `infant`, `soft_food`) เป็น
**มิติตั้งฉาก — คนหนึ่งเป็นได้หลายกลุ่ม บวกกันเกิน total ได้** ซึ่ง `deriveSessionHeadcountFromOccupancy`
ใช้ mapping เดียวกันกับเป้าของ session (ดู Q2)

## Change

**ก่อน:** โค้ดบวกยอดผลิตเต็มจำนวนให้ทุกแท็กที่เมนูมี (นับซ้ำ), `isCompleted = actualYield >= target`

**หลัง (เสนอ):** จัดสรรจานแบบ **priority fill** — ตอนบันทึกยังกรอก **ยอดรวมช่องเดียว** เหมือนเดิม
ระบบจัดสรรให้เอง (คำนวณตอนแสดงผลเท่านั้น)

เหตุผล: อาหารหลายแท็ก "กินข้ามลง" ได้ทางเดียว (ข้าวฮาลาลคนทั่วไปกินได้ แต่กลับกันไม่ได้) จึงเติม
กลุ่มที่มีข้อจำกัดให้ครบก่อน เศษที่เหลือค่อยไปกลุ่มที่ยืดหยุ่น — ตรงกับการแจกจริงหน้างาน

### กติกา

| #   | กติกา                                                                                                                                          |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | ลำดับเติม: `infant` (เด็ก/ทารก) → `soft_food` (ผู้ป่วย/อาหารอ่อน) → `halal` (ฮาลาล) → `volunteer` (เจ้าหน้าที่/อาสาสมัคร) → `regular` (ทั่วไป) |
| R2  | เติมได้เฉพาะกลุ่มที่อยู่ในแท็กของเมนูนั้น                                                                                                      |
| R3  | หลายเมนูในเซสชันเดียวกัน: จัดสรรจากเมนูที่แท็กแคบที่สุดก่อน (เช่น เมนูอาหารอ่อนล้วน) เพื่อไม่ให้เมนูแท็กกว้างกินโควต้ากลุ่มเฉพาะ               |
| R4  | จานที่เหลือหลังเติม**ทุกกลุ่มในแท็กของเมนูนั้น**เต็ม → แสดงเป็น "เกิน" ในแถวรวม _(ขยายความจาก issue ให้สอดคล้องกับ R2 — ดู Q1)_                |
| R5  | กลุ่มที่เป้า = 0 → รวมเป็นแถวเดียว "ไม่มีเป้าหมาย" สีเทา ค่า "—" และ **ไม่นับ**ในตัวหาร "x/y กลุ่มครบ"                                         |
| R6  | หน่วยเดียวกันทั้งตาราง: เป้าหมาย (จาน) vs ได้รับ (จาน); สมมติฐาน 1 คน = 1 จาน/มื้อ _(ถูกต้องเมื่อกลุ่มไม่ซ้อนกัน — ดู Q2)_                     |
| R7  | แสดงส่วนต่างต่อกลุ่ม (`ครบ` / `ขาด N`) และแถวรวมท้ายตาราง: เป้ารวม vs จานผลิตจริง (+ `เกิน N` ถ้ามี)                                           |

## Open questions (ต้องให้เจ้าของโครงการตัดสิน — issue ไม่ได้ระบุ)

**Q1 — ส่วนเกินของเมนูแท็กแคบ ข้ามไปกลุ่มนอกแท็กได้หรือไม่:** เมนูแท็กแคบ (เช่น `soft_food`
อย่างเดียว) ที่ผลิตเกินเป้าของกลุ่มตัวเอง ส่วนเกินควร

- **(ก) เป็น "เกิน"** ตาม R2 + R4 อย่างเคร่งครัด — จานนอกแท็กไม่นับให้กลุ่มอื่น _(ข้อเสนอ)_, หรือ
- **(ข) ไหลไปกลุ่มที่ไม่ได้อยู่ในแท็กของเมนู** ตามหลัก "กินข้ามลง" (เช่น อาหารอ่อนให้คนทั่วไปกินได้)
  — ถ้าเลือกข้อนี้ต้องแก้ R2 และต้องกำหนดว่ากลุ่มไหนกินข้ามลงไปกลุ่มไหนได้

issue ระบุ R2 ไว้ชัด แต่ไม่ได้ยกตัวอย่างเมนูแท็กแคบที่ผลิตเกิน จึงขอยืนยัน

**Q2 — กลุ่มเป้าหมายซ้อนกัน:** `deriveSessionHeadcountFromOccupancy`
(`kitchen/domain/occupancy.ts:34`) นับ `halal` = มุสลิม, `infant` = มี `infant` ใน special needs,
`soft_food` = มี `bedridden`/`chronic_illness`/`elderly` — สามกลุ่มนี้ซ้อนกันได้ทุกคู่ (เช่น ทารกมุสลิม,
ผู้สูงอายุมุสลิม, ทารกที่ป่วยติดเตียง) มีแค่ `regular` ที่แยกขาด (ไม่ใช่มุสลิม ไม่ใช่ทารก ไม่ต้องการ
อาหารอ่อน) ส่วน `volunteer` ไม่ได้มาจาก occupancy (derive เป็น 0 แล้วกรอกเอง) และไม่อยู่ใน `total`
ผลคือ Σ เป้าทุกกลุ่มอาจ**ไม่เท่ากับ** `target_headcount.total` และสมมติฐาน "1 คน = 1 จาน" (R6) ใช้ได้
เฉพาะเมื่อไม่มีคนซ้อนกลุ่ม — ตัวอย่างใน issue (47 + 235 = 282 = total) ไม่มีการซ้อน จึงไม่เห็นปัญหานี้

- **(ก) ใช้เป้าแต่ละกลุ่มตามที่เก็บ และเป้ารวม = Σ เป้าทุกกลุ่ม** _(ข้อเสนอ — ไม่ต้องแก้ข้อมูล)_ —
  คนซ้อนกลุ่มจะถูกนับเป็นหลายจาน (ทารกมุสลิม 1 คน = 1 จานทารก + 1 จานฮาลาล) จึงอาจเกินความต้องการจริง
  และหัวตาราง "รวม N จาน" อาจไม่ตรงกับ "เป้าหมายรวม N คน" บนหัวการ์ดเดียวกัน
- **(ข) ทำให้กลุ่มแยกขาดตั้งแต่ตอน derive** — นับแต่ละคนเข้ากลุ่มแรกที่ตรงตามลำดับ R1 — แก้
  `deriveSessionHeadcountFromOccupancy` ซึ่งอยู่นอกขอบเขต issue #770 และควรเปิด CR แยก

| D3  | เมนูที่แท็กกว้างเท่ากัน จัดสรรตามลำดับที่ได้รับข้อมูลมา (stable sort)                        | R3 ไม่ได้กำหนดตัวตัดสินเมื่อแท็กเท่ากัน; ลำดับนี้ไม่ทำให้ยอดรวมเปลี่ยน แค่อาจเปลี่ยนว่ากลุ่มไหนขาดเมื่อจานไม่พอ |
| D4  | แถวรวม ช่อง "ได้รับ" แสดง **ยอดผลิตจริงทั้งหมด** (จานที่จัดสรรได้ + เกิน) ต่อท้าย "· เกิน N" | ตามถ้อยคำ issue "เป้ารวม vs จานผลิตจริง (+ เกิน N)" — จึงอาจไม่เท่ากับผลรวมของแถวกลุ่มเมื่อมีส่วนเกิน           |

## Impact

- `frontend/src/lib/features/kitchen/domain/meal-calc.ts` — เขียนใหม่ `computeSessionGroupProgress`
  (priority-fill) และเปลี่ยน return shape (`actualYield` → `received` + `shortfall`, `hasTarget`,
  ยอดรวม, `surplus`)
- `frontend/src/lib/features/kitchen/domain/kitchen.test.ts` — test เดิม (`:431-493`) ยืนยันพฤติกรรม
  นับซ้ำอยู่ (ฮาลาลได้ 50 จาก yield 50) ต้องแก้ค่าที่คาดหวัง และเพิ่มเคส: เมนูหลายแท็ก, เป้า 0,
  จานไม่พอ, จานเกิน, หลายเมนูแท็กซ้อนกัน
- `frontend/src/lib/features/kitchen/ui/MealSessionList.svelte` — ปรับตาราง: หน่วย, หัวข้อ,
  แถว "ไม่มีเป้าหมาย" แถวเดียว, ส่วนต่างต่อกลุ่ม, แถวรวม
- ไม่กระทบ data model / `schema_v` — ไม่มี field ใหม่ ใช้ `target_tags` + `target_headcount` +
  `actual_yield`/`served` ที่มีอยู่แล้ว
- ไม่มีเอกสารเดิมใน `docs/` ที่ต้องแก้ตามกติกานี้ — CR นี้จึงเป็นบันทึกกติกาแรก; ถ้าเจ้าของโครงการ
  ต้องการ spec ถาวร (เช่น เพิ่มหัวข้อ `meal_session` ใน `docs/data/schema.md`) ให้เปิดเป็นงานแยก
- ผู้ใช้หน้างานที่คุ้นกับตัวเลขเดิม (ซึ่งผิด) จะเห็นตัวเลขเปลี่ยน — ควรแจ้งทีมครัวตอน deploy

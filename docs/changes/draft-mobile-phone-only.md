# draft-mobile-phone-only — เบอร์มือถือ 10 หลักทั้งระบบ

> **สรุป (TL;DR):**
>
> - **เปลี่ยนอะไร:** ทุกช่องที่กรอกหรือค้นด้วยเบอร์ในระบบต้องเป็นมือถือ 10 หลัก (`^0\d{9}$` หลัง normalize) เลิกรับเบอร์บ้าน 9 หลัก
> - **ครอบคลุม:** บัญชีผู้ใช้ (ถอน CR-202), ผู้อพยพ, kiosk, ค้นหาครอบครัว, ค้นหาฝั่ง FastAPI, API ภายนอก
>   - เบอร์จิตอาสาทำแล้วใน draft-volunteer-mobile-phone (#951)
> - **ข้อมูลเดิม:** ไม่ migrate เอกสารเดิมอ่านได้ แต่บันทึกฟอร์มใหม่ต้องแก้เป็นมือถือหรือเว้นว่าง
> - **กระทบภายนอก:** API ภายนอกปฏิเสธเบอร์ 9 หลัก ต้องแจ้งพาร์ทเนอร์ก่อน deploy · ไม่ bump `schema_v`

---

## Why

- **คำสั่ง:** @net-lynx สั่งเมื่อ 2026-10-28 ให้ "เอาเบอร์ 9 หลักที่เป็นเบอร์บ้านออกเลย" และผู้รับงานยืนยันว่าขอบเขตคือทั้งระบบ
- **เบอร์บ้านระบุตัวคนไม่ได้:** เบอร์บ้านใช้ร่วมกันหลายคน แต่เบอร์ในระบบใช้ระบุตัวตนและค้นหา (`phone_hash` กันซ้ำ, login ด้วยเบอร์, ค้นหาครอบครัว, kiosk)
- **ทางเดียวกับ #880:** สอดคล้องกับ #880 ทาง B (เบอร์จิตอาสา) และทำให้กฎเบอร์ทั้งระบบเหลือชุดเดียว

## Change

### FR

- **FR-1:** กฎเบอร์กลางของระบบ
  - normalize ก่อน: ตัดช่องว่าง ขีด วงเล็บ และ `+66` / `66` → `0` (CR-148)
  - หลัง normalize ต้องตรง `^0\d{9}$`
  - ฝั่ง frontend ใช้ schema ตัวเดียว (ต่อยอดจาก `lib/utils/volunteer-phone.ts` ของ #951)
  - ฝั่ง FastAPI ใช้ regex จุดเดียว
- **FR-2:** ช่องกรอกเบอร์ทุกจุดใช้ FR-1 ได้แก่
  - บัญชีผู้ใช้ (ฟอร์มผู้ใช้, `/me`, `user-service`)
  - เบอร์ผู้อพยพและหัวหน้าครัวเรือน (onsite, pre-register, BFF registrations)
  - kiosk (ลงทะเบียน walk-in)
  - API ภายนอก (EXT bookings)
- **FR-3:** ช่องที่เดิมเว้นได้ยังเว้นได้ เช่นเบอร์ผู้อพยพ "ไม่มี" → `null` (schema.md evacuee `phone`) และ walk-in จิตอาสา
- **FR-4:** ช่องค้นหาด้วยเบอร์ใช้ FR-1 ได้แก่
  - kiosk (เช็คอิน, พิมพ์บัตรซ้ำ, บัตรจิตอาสา)
  - ค้นหาครอบครัวใน public portal
  - FastAPI search
- **FR-5:** บัญชีผู้ใช้ `phone` เป็นมือถือ 10 หลักหรือ `null`
  - ห้ามซ้ำข้ามบัญชี และห้ามชน `name` ของบัญชีอื่น (กลับไปตาม CR-105)
  - ใช้ login และกู้รหัสได้
- **FR-6:** ข้อความ error เดียวกันทั้งระบบ: "เบอร์มือถือต้องเป็นตัวเลข 10 หลักขึ้นต้นด้วย 0" (ฝั่ง API ภายนอกใช้รูปแบบ error เดิมของ API)

### ข้อมูลเดิม (ไม่ migrate)

- **FR-7:** เอกสารที่เก็บเบอร์ 9 หลักไว้แล้ว (บัญชี, ผู้อพยพ, จิตอาสา) ยังอ่านและแสดงได้ ไม่ error
- **FR-8:** เปิดฟอร์มแก้ไขเอกสารเหล่านั้นแล้วบันทึก ต้องแก้เบอร์เป็นมือถือ หรือเว้นว่างถ้าช่องนั้นเว้นได้
- **FR-9:** ค้นด้วยเบอร์ 9 หลักไม่ได้แล้ว ให้ค้นด้วยชื่อ เลขบัตร หรือรหัสแทน

## Acceptance

- **AC-1:** ทุกจุดใน FR-2/FR-4 ปฏิเสธ `022222222` และ `02-222-2222` ส่วน `081-234-5678` และ `+66812345678` ผ่านและเก็บเป็น `0812345678`
- **AC-2:** ฟอร์มผู้ใช้และ `/me` ไม่รับเบอร์บ้าน และมือถือยังห้ามซ้ำ
- **AC-3:** ผู้อพยพที่ไม่มีเบอร์ยังลงทะเบียนได้
- **AC-4:** API ภายนอกตอบ validation error สำหรับเบอร์ 9 หลัก
- **AC-5:** เอกสารเดิมที่มีเบอร์ 9 หลักยังเปิดดูได้ บันทึกฟอร์มแล้วต้องแก้เบอร์ก่อน

## Impact

- **code:** ตามตารางใน #991
- **test:**
  - frontend unit test ทุก schema/route ที่แก้
  - backend `backend/tests/` (search_query, thirdparty_bookings)
  - e2e ที่ใช้เบอร์บ้าน (ถ้ามี)
- **ภายนอก:** พาร์ทเนอร์ที่ใช้ API EXT bookings ต้องได้รับแจ้งก่อน deploy
- **ข้อมูลเดิม:** ค้นด้วยเบอร์ 9 หลักไม่ได้ เจ้าหน้าที่ต้องแก้เบอร์เมื่อเจอ

## Migration

ไม่มี ไม่แก้เอกสารเดิมและไม่ bump `schema_v` (ตาม FR-7 ถึง FR-9)

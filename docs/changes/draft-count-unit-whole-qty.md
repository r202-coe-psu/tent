# หน่วยนับรับเฉพาะจำนวนเต็ม และจำนวนที่ระบบคำนวณปัดขึ้น

> **สรุป:** จำนวนของหน่วยที่ `unit_of_measure.dimension === 'count'` (ขวด กล่อง ถุง ซอง กระป๋อง ถัง
> ชิ้น ฯลฯ) ต้องเป็นจำนวนเต็มทุกจุดที่ผู้ใช้กรอก หน่วย `mass` / `volume` / อื่นๆ ยังรับทศนิยมได้
> จำนวนที่ระบบคำนวณเอง (เช่น สเกลสูตรตามจำนวนคน) ปัดขึ้นเป็นจำนวนเต็มทุกหน่วย ไม่มี migration

## Why

ตอน roleplay 23/10/69 ผู้ใช้กรอก "1.5 ขวด" ในวัตถุดิบได้ ระบบเก็บจำนวนเป็น `qty_str` (CR-038)
ซึ่งรับทศนิยมทุกหน่วย และช่องกรอกใช้ `step="any"` ทั้งหมด ผลคือสต็อกมีเศษขวด / เศษกล่อง
ที่หยิบจริงไม่ได้ แบบเดียวกับปัญหาเศษแก๊ส 0.001 kg ที่ต้องเพิ่มปุ่ม "ตัดเศษเหลือทิ้ง" ใน CR-086

เจ้าของโครงการเลือก **ทาง A** ใน #805: หน่วย `count` รับเฉพาะจำนวนเต็มทุกจุด ถ้าสูตรต้องใช้น้อยกว่า
หนึ่งหน่วย ให้ใช้หน่วย `mass` / `volume` (g, ml) แทน

## Change

### FR-1 — กฎจำนวนเต็มตาม dimension

| | Before | After |
| --- | --- | --- |
| หน่วย `count` | รับทศนิยม (`1.5` ขวด) | รับเฉพาะจำนวนเต็ม (`1`, `2`) — ทศนิยมแสดง error "หน่วยนับต้องเป็นจำนวนเต็ม" |
| หน่วย `mass` / `volume` / `length` / `energy` | รับทศนิยม | ไม่เปลี่ยน |
| หน่วยที่หา dimension ไม่เจอ (label เก่า) | รับทศนิยม | ไม่เปลี่ยน — ไม่บังคับ |

- เกณฑ์คือ `dimension` ของ `unit_of_measure` (master ใน CouchDB ก่อน แล้วค่อย fallback
  `FALLBACK_UNIT_DEFINITIONS`)
- กฎอยู่ที่ `catalog/domain` จุดเดียว ทุกฟอร์มเรียกใช้ร่วมกัน
- ช่องกรอกจำนวนของหน่วย `count` ใช้ `step="1"` แทน `step="any"`

### FR-2 — จุดที่บังคับ

- **ครัว:** สูตร (recipe — ค่าต่อ standard batch ที่ผู้ใช้กรอก), production board (ตั๋วเบิก),
  รับอาหารสำเร็จ (yield receipt)
- **คลัง/บริจาค:** รับของ, รับบริจาค, แก้รายการบริจาค (หน้า public ใช้รายการหน่วย built-in),
  โอน, แจกจ่าย, ปรับสต็อก, cycle count
- **แจกจ่าย/ตั๋ว:** เลือก lot, จัดสรรตั๋วฝั่งคลัง

ข้อยกเว้น:

- **meal plan (custom ingredient)** — ช่องกรอกเป็นอัตราต่อคน (เช่น 0.5 ฟองต่อคน) ไม่ใช่จำนวนสต็อก
  จึงไม่บังคับจำนวนเต็ม ยอดรวม (อัตรา × จำนวนคน) ปัดขึ้นตาม FR-3
- **ปรับสต็อก / cycle count** — บังคับเฉพาะ "จำนวนที่นับได้จริง" ส่วน delta ที่ระบบคำนวณอาจเป็นเศษได้
  (นับได้ 2 จาก lot ที่มี 2.5 ขวด → delta −0.5) และถ้ายอดนับตรงกับระบบไม่ถือว่าผิด
- **ฟอร์มแจกจ่ายชุด food-supplies / ตั๋ว / คืนของ** รับเฉพาะจำนวนเต็มทุกหน่วยอยู่แล้วก่อน CR นี้ — ไม่เปลี่ยน

### FR-3 — จำนวนที่ระบบคำนวณเองปัดขึ้น

- ปัดขึ้นเป็นจำนวนเต็ม**ทุกหน่วย** (ตามที่ `meal-calc` ทำอยู่แล้ว) — ตัวอย่าง: สูตรใช้ซอส 1 ขวดต่อ
  100 คน มื้อนี้ 150 คน = 1.5 → **2 ขวด**; ข้าว 12.3 g/คน × 7 คน = 86.1 → **87 g**
- ส่วนที่เกินจากการปัดถือว่าใช้ไปกับรอบนั้น ไม่คืนเศษ
- จุดที่ปัด: ยอดข้าว / custom ingredient / สูตรตามจำนวนคนใน `meal-calc` และค่าเริ่มต้นของตั๋วเบิกบน
  production board (`scaleRecipeIngredientQty` — เดิมปัด 4 ตำแหน่ง half-up)
- ข้อยกเว้น: ค่าเพดาน (ปุ่ม "ทั้งหมด" / clamp ไม่ให้เกินยอดคงเหลือ) ปัด**ลง**สำหรับหน่วย `count`
  เพราะปัดขึ้นจะเกินของที่มีจริง

## Impact

- **Code:** domain helper ใหม่ใน `catalog/domain` + export ผ่าน barrel; ฟอร์มตามรายการใน FR-2;
  `kitchen/domain/meal-calc.ts` เปลี่ยนจาก float `Math.ceil` เป็น Decimal (แก้ 300 × 0.07 ได้ 22 แทน 21)
- **Test:** unit test ของกฎ (count / mass / ไม่รู้ dimension / ปัดขึ้น) + test ของฟอร์มที่มี
- **Docs:** ไม่เปลี่ยน `docs/data/schema.md` — รูปร่าง doc เหมือนเดิม แค่ validation เข้มขึ้นตอนบันทึก

## Migration

N/A — ไม่ bump `schema_v` และไม่เขียน migration ข้อมูลเดิมที่มีเศษยังอ่านได้ตามเดิม
บังคับจำนวนเต็มตอนบันทึกครั้งถัดไป เศษที่ค้างในสต็อก (เช่น 3.5 ขวด) แก้ผ่านฟอร์มปรับสต็อกหรือ cycle count
โดยกรอกยอดที่นับได้จริงเป็นจำนวนเต็ม (ปุ่ม "ตัดเศษเหลือทิ้ง" ของ CR-086 มีเฉพาะถังแก๊สหน่วย kg)
lot เก่าที่มีเศษอาจจัดสรรครบไม่ได้ถ้ายอดที่ขาดน้อยกว่า 1 — ต้องเลือก lot อื่นหรือปรับสต็อกก่อน

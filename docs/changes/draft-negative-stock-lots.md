# ล็อตติดลบไม่หยุดงาน — แสดงพร้อมคำเตือน ห้ามตัดต่อ และแก้ด้วยการปรับยอด

> **สรุป (TL;DR):**
>
> - **Phase 1 (รุ่นนี้):** `projectStockLotBalances` ไม่ throw เมื่อล็อตติดลบอีกต่อไป — ตารางสต็อกและหน้าตรวจนับแสดงล็อตติดลบพร้อมคำเตือน
>   แทนการซ่อนทั้งสินค้า (แก้ CR-190 FR-6). ล็อตติดลบเลือกเบิก / ตัดยอดไม่ได้; ล็อตอื่นของสินค้าเดียวกันใช้ได้ปกติ. การตรวจล็อตก่อนเขียน (CR-190 FR-4, CR-175) คงเดิม
> - **Phase 2 (follow-up):** หน้า "ล็อตที่ต้องแก้" สำหรับ `system_admin` / `warehouse_staff` / `supply_coordinator` และการแก้ด้วยแถว `adjust` บวกเข้า**ล็อตที่ติดลบเดิม**
>   (ย้ายยอดขาดจากล็อตอื่น หรือยืนยันจากการนับ) ไม่เกินยอดที่ติดลบ (แก้ CR-190 FR-3 และ schema.md `lot_ref`)
> - **ทำไม:** ล็อตติดลบเกิดได้ตามสถาปัตยกรรม (edge fallback, writer ที่ไม่จอง claim) — กันไม่ได้ 100% จึงต้องทนได้ ตรวจเจอ และชดเชย
> - **schema:** ไม่เพิ่ม field / enum · ไม่ bump `schema_v` · ไม่มี migration

---

## Why

- `projectStockLotBalances` ถือว่าล็อตติดลบเป็นประวัติที่ replay ไม่ได้ แล้ว throw `StockLotIntegrityError` →
  สินค้าทั้งตัวหายจากตารางสต็อกและหน้าตรวจนับ (CR-190 FR-6) และแก้ด้วยการปรับยอดไม่ได้ เพราะการปรับเพิ่มต้องเป็นล็อตใหม่ (CR-190 FR-3)
- ล็อตติดลบเกิดได้โดยไม่มีใครทำผิด:
  - **edge fallback:** ตอน WAN ล่ม central กับ edge รับการตัดล็อตเดียวกันคนละฝั่ง — claim แบบใดก็กันไม่ได้
  - **writer ที่ตัดด้วย `lot_ref` โดยไม่จอง claim:** ticket dispatch (`dispatchTicket`), item merge (`planItemMerge`),
    ฟอร์มปรับยอด / ตรวจนับ (CR-190 Impact "ความพร้อมกัน")
- ทาง A (ขยาย `stock_lot_reservation` claim) กันได้ไม่ครบทุกคู่ writer และต้องแก้ทั้ง §2.24, Zod และ VDU; ทาง B / C ไม่แก้ปัญหาการซ่อนสินค้า (#881)
- แนวทาง: ยอมให้เกิด → ตรวจจับ → ชดเชยด้วยแถวใหม่ (compensating transaction) — ledger เป็น append-only อยู่แล้ว

## Requirements — Phase 1 (รุ่นนี้)

### Projection

- **FR-1** — `projectStockLotBalances` ต้องคืนล็อตที่ `qty < 0` ได้ โดยไม่ throw; `isNegativeLot(lot)` (`qty < 0`) export ผ่าน barrel `$lib/features/operations`
- **FR-2** — แถวขาออกที่มี `lot_ref` ตัดล็อตนั้น**เต็มจำนวน** ไม่ clamp ที่ 0 — ยอดล็อตติดลบได้
- **FR-3** — แถวขาออก legacy (ไม่มี `lot_ref`) ตัดล็อตยอดบวกตามลำดับ legacy เดิม (comparator FEFO→FIFO ไม่เปลี่ยน — CR-143 §A decision);
  ส่วนที่เกินยอดรวมของทุกล็อต (ส่วนขาด) หักจาก**ล็อตสุดท้ายที่ตัด** ทำให้ล็อตนั้นติดลบ
- **FR-4** — ประวัติต่อไปนี้ยังเป็นข้อมูลเสีย: throw `StockLotIntegrityError` → ข้ามเฉพาะสินค้านั้นและแจ้งชื่อ (พฤติกรรมเดิมของ CR-190 FR-6):
  1. ล็อตเดียวกันถูกอ้างด้วย `item_id` หรือ `unit` ต่างกัน
  2. `distribution_return` อ้างล็อตที่ไม่มีในประวัติ
  3. แถวขาออกอ้าง `lot_ref` ที่ไม่มีในประวัติ
  4. แถวขาออก legacy ที่ไม่มีล็อตยอดบวกให้ตัดเลย (ไม่มี "ล็อตสุดท้ายที่ตัด")
- **FR-5** — ประวัติที่ replay ผ่านก่อน CR นี้ต้องได้ยอดรายล็อตเท่าเดิมทุกล็อต

### หน้าจอ

- **FR-6** — ตารางสต็อกแสดงสินค้าที่มีล็อตติดลบตามปกติ; ล็อตติดลบแสดงยอดติดลบพร้อมคำเตือน "ล็อตนี้ยอดติดลบ — ต้องแก้ยอด";
  ยอดรวมของสินค้า = ผลรวม `qty` ใน ledger (`stockBalance`) เหมือนเดิม
- **FR-7** — หน้าตรวจนับแสดงสินค้าและล็อตติดลบพร้อมคำเตือนเดียวกับ FR-6; ล็อตติดลบ**แสดงอย่างเดียว** — ไม่มีช่องกรอกยอดนับ
  และไม่สร้างแถว `count_mismatch` ของล็อตนั้น (การแก้ด้วยการนับอยู่ที่ FR-17 ของ Phase 2)
- **FR-8** — ล็อตติดลบเลือกเพื่อเบิกหรือตัดยอดไม่ได้ทุกจุด: ฟอร์มเบิกตรง, picker ของตั๋ว (`PhysicalLotPicker`), ฟอร์มปรับยอด,
  แผนแบ่งล็อตอัตโนมัติ (`planLotSplit`); ล็อตอื่นของสินค้าเดียวกันเลือกได้ปกติ

### ตรวจก่อนเขียน

- **FR-9** — การตรวจล็อตก่อนเขียน (CR-190 FR-4, CR-175) คงเดิมทุกข้อ. แถวตัดยอดที่อ้างล็อตติดลบ → `assertLotWriteOffsFit` ปฏิเสธด้วยข้อความ
  "ล็อตที่เลือกติดลบ (−N หน่วย) ตัดยอดเพิ่มไม่ได้ — ต้องแก้ยอดล็อตนี้ก่อน" และไม่เขียนแถวใดในคำขอนั้น
- **FR-10** — ล็อตที่ทั้งหมดอายุและติดลบ: UI ไม่แนะนำให้ปรับยอดออก (CR-195 FR-X3) — แสดงคำเตือนล็อตติดลบตาม FR-6 แทน

## Requirements — Phase 2 (follow-up)

### หน้า "ล็อตที่ต้องแก้"

- **FR-11** — หน้าในเมนูคลังแสดงล็อตติดลบทุกล็อตของศูนย์: สินค้า, ป้ายล็อต (`lot_no` / ที่เก็บ / วันหมดอายุ), ยอดติดลบ, แถวต้นเหตุ
  (`_id`, `reason`, `ref_id`), ผู้ทำ (`created_by` ของแถวต้นเหตุ) และเวลา (`occurred_at`)
- **FR-12** — แถวต้นเหตุ = แถวขาออกล่าสุดที่ replay แล้วทำให้ยอดล็อตเปลี่ยนจาก ≥ 0 เป็น < 0
- **FR-13** — หน้าและปุ่มแก้แสดงเฉพาะ `system_admin`, `warehouse_staff` และ `supply_coordinator`; `shelter_manager` และ role อื่นไม่เห็น

### การแก้

- **FR-14** — การแก้ = แถว `adjust` ใหม่ที่ `qty > 0`, `lot_ref` = ล็อตที่ติดลบ, `ref_id = null`, `note` มี `_id` ของแถวต้นเหตุ; ไม่แก้หรือลบแถวเดิม
- **FR-15** — จำนวนที่แก้ `X`: `0 < X ≤ |ยอดล็อต|` ณ ตอนบันทึก — หลังแก้ ยอดล็อต ≤ 0
- **FR-16** — **ย้ายยอดขาด (default):** `+X` เข้าล็อตที่ติดลบ และแถว `adjust` `−X` (มี `lot_ref`) จากล็อตอื่นของสินค้าและหน่วยเดียวกัน
  ที่ระบบเสนอตามลำดับ CR-143 §A (`planLotSplit` — ข้ามล็อตหมดอายุและล็อตติดลบ); ผลรวมแถว `−X` = `X`; ยอดรวมสินค้าไม่เปลี่ยน.
  ทุกแถวของคู่ย้ายยอด (`+X` และ `−X`) ใช้ `adjust_reason: other` และ `note` ตาม FR-14 — ไม่เพิ่ม enum
- **FR-17** — **ยืนยันจากการนับจริง:** `+X` แถวเดียว `adjust_reason: found`; `note` = `_id` แถวต้นเหตุ + หมายเหตุของผู้แก้ (บังคับ); ยอดรวมสินค้าเพิ่ม `X`
- **FR-18** — ก่อนบันทึกต้องผ่าน: ล็อตเป้าหมายมีใน projection ล่าสุด, `item_id` / `unit` ตรง, ยังติดลบ, `X ≤ |ยอดล็อต|`;
  แถว `−X` ของ FR-16 ผ่านกติกา CR-190 FR-4. ไม่ผ่าน → ไม่เขียนแถวใดเลย พร้อมข้อความภาษาไทย
- **FR-19** — เขียนทุกแถวของการแก้หนึ่งครั้งใน `bulkDocs` เดียว; ล้มบางแถว → ไม่ rollback และรายงานแถวที่เขียนแล้ว / ยังไม่เขียน (แบบ CR-143 FR-A9)

### Validation และสิทธิ์

- **FR-20** — ฟอร์มปรับยอดทั่วไป (`adjustInputSchema`) ยังปฏิเสธ `lot_ref` บนการปรับเพิ่ม (CR-190 FR-3 เดิม); เฉพาะ input ของการแก้ล็อตติดลบรับ
  `lot_ref` บนแถวบวก และ `createParsedStockLedger` ยอม `lot_ref ≠ _id` เฉพาะกรณีนี้
- **FR-21** — `_design/access`: แถว `reason: 'adjust'` ที่ `qty > 0` และมี `lot_ref ≠ _id` → ผู้เขียนต้องผ่าน
  `isRole('warehouse_staff') || isRole('supply_coordinator')` (`isRole` ครอบ `system_admin`; **ไม่รวม** `shelter_manager` ต่างจาก gate `isStaff` เดิม),
  `lot_ref` ขึ้นต้น `stock_ledger:` และ `note` ไม่ว่าง; role อื่นทั้งหมด (รวม `shelter_manager`) → `forbidden`
- **FR-22** — ไม่เพิ่ม field / enum: `ref_id` ของ `adjust` คง `null` (ตาราง "`reason` → `ref_id`"), ใช้ `note` เก็บแถวต้นเหตุ

### แจ้งผู้บันทึก

- **FR-23** — หลังบันทึกรายการที่ตัดล็อต (#855 Requirement 3) ระบบเช็คยอดล็อตที่ตัดซ้ำ; ล็อตใดติดลบ → toast บอกผู้กดว่ารายการบันทึกสำเร็จแล้ว
  ไม่ต้องทำใหม่ และล็อตนั้นรอแก้ที่หน้า "ล็อตที่ต้องแก้"

# CR-223 — ฐานจำนวนคนของการวิเคราะห์เสบียง = ผู้ประสบภัย + staff + จิตอาสา

> **สรุป:** แท็บวิเคราะห์เสบียง (Food Sphere) เปลี่ยนฐานคำนวณจาก "ผู้ประสบภัยเท่านั้น" เป็น "ทุกคนที่อยู่ในศูนย์ตอนนี้" โดยใช้ฟังก์ชันเดียวกับที่ครัวใช้อยู่แล้ว และบันทึกกติกาการนับของครัวจาก #960 ย้อนหลังไว้ในที่เดียว

## Why

ตารางกลุ่มน้ำดื่มสะอาดและกลุ่มอื่นคำนวณเป้าหมายรายวันจาก `in_shelter` ซึ่งนับเฉพาะผู้ประสบภัย
แต่คนที่กินและใช้ของในศูนย์จริงมีทั้งเจ้าหน้าที่ประจำศูนย์และจิตอาสาที่เช็คอินอยู่

ผลคือเป้าหมายรายวันและ DOC ต่ำกว่าความเป็นจริง — **ระบบบอกว่าของพอ ทั้งที่อาจไม่พอ** ซึ่งเป็นความเสี่ยงต่อการวางแผนเสบียงโดยตรง จึงติด `priority:critical` ใน #1068

ครัวแก้เรื่องนี้ไปแล้วตั้งแต่ #960 (issue #806) โดยนับ staff และจิตอาสาเข้าไปด้วย แต่ตอนนั้นยังไม่มี CR บันทึกกติกาไว้ และสต็อกยังไม่ได้ทำตาม ทำให้สองหน้าจอของระบบเดียวกันคิดจากฐานคนคนละชุด

## Change

### 1. กติกาการนับ (บันทึกของเดิมจาก #960 + ใช้กับสต็อกด้วย)

| กลุ่ม | นับใคร |
| --- | --- |
| ผู้ประสบภัย | `in_shelter` — `current_stay.status` เป็น `active` หรือ `room_confirmed` (ตาม [CR-224](../01-core/CR-224-in-shelter-headcount.md)) |
| จิตอาสา | ที่ `checked_in` และ `current_shelter_code` ตรงกับศูนย์นี้ |
| staff | บัญชีที่มี capability ของศูนย์นี้ เป็น active และไม่ใช่ `personnel_type = volunteer` (`listShelterStaff`) |

จิตอาสาที่มีบัญชีผู้ใช้ด้วย (Staff-Capable Volunteer) **นับเป็นจิตอาสาอย่างเดียว ไม่นับซ้ำเป็น staff**

นับ **ณ ขณะนี้** ไม่ใช่ค่าสูงสุดของวันหรือค่าเฉลี่ย เพื่อให้ตัวเลขบนหน้าครัวและหน้าสต็อกตรงกันเสมอ

คนที่อยู่ไม่เต็มวันนับเป็น 1 คนเต็ม เหมือนที่ครัวทำ

### 2. ที่อยู่ของกติกา

ย้าย `countShelterPeople` จาก `kitchen/domain/occupancy.ts` ไปไว้ที่
`shared/domain/shelter-people.ts` แบบเดียวกับ `in-shelter.ts` แล้วให้ทั้งครัวและแท็บสต็อกเรียกตัวเดียวกัน

**ห้ามเขียนกติกาซ้ำในแท็บ SOP** เพื่อให้คำตัดสินเรื่องวิธีนับ staff ในอนาคตแก้ที่เดียวจบ

พฤติกรรมของครัวต้องไม่เปลี่ยนจากการย้ายครั้งนี้

### 3. การกระจายเข้า target segment

staff และจิตอาสา **ไม่กระจายตามสัดส่วนอายุของผู้ประสบภัย** — `headcountsFromAgeGroups` รับยอดรวม
ส่วน `ageGroups` ยังเป็นของผู้ประสบภัยเท่านั้น ส่วนที่เกินจึงตกลงที่ segment `ALL` ซึ่งเป็นเกณฑ์ผู้ใหญ่ทั่วไป
เทียบได้กับที่ครัวรวม staff + จิตอาสาไว้ในกลุ่ม `volunteer` ของ `MealSessionHeadcount`

ข้อ 3 ของ CR-130 ที่เขียนว่า "ประชากรทุกคนต้องถูกนับรวมเพียงครั้งเดียว (Total headcounts = Effective occupancy)"
ยังคงเป็นจริง แต่ **ความหมายของ Effective occupancy เปลี่ยนจาก "ผู้ประสบภัย" เป็น "ทุกคนที่อยู่ในศูนย์"**

### 4. การแสดงผล

แถบสรุปและบรรทัด "ฐานคำนวณ" แสดงยอดรวม

```
ทั้งหมด 335 คน
```

ที่มาของตัวเลขอยู่ใน tooltip ของยอดรวม เปิดได้จากการชี้เมาส์ การแตะบนจอสัมผัส และการโฟกัสด้วยคีย์บอร์ด

```
ผู้ประสบภัย 300 คน
เจ้าหน้าที่ 20 คน
จิตอาสา 15 คน
```

ถอดป้าย **"อัตราครองเตียง"** ออกจากแถบสรุปของแท็บนี้ เพราะป้ายแสดงจำนวนผู้ประสบภัยซ้ำกับแถวด้านบน และเป็นจำนวนคน ไม่ใช่อัตราต่อเตียงตามชื่อ

ป้ายชื่อเดียวกันในหน้าข้อมูลศูนย์สาธารณะ (`public-shelter-details.ts`) ไม่อยู่ในขอบเขตของ CR นี้

## สิ่งที่ยังไม่ตัดสินใน CR นี้

ทีมรับทราบแล้วว่าการนับ staff จากบัญชีผู้ใช้ให้ตัวเลข**สูงเกินจริง** เพราะรวมคนที่วันนั้นไม่ได้มาปฏิบัติงาน
แต่ระบบยังไม่มีการลงเวลาเข้างานของ staff จึงยังไม่มีแหล่งข้อมูลที่ดีกว่านี้

เรื่องต่อไปนี้ยกไปเป็น issue แยกให้เจ้าของโครงการตัดสิน

- วิธีนับ staff ที่ถูกต้องในระยะยาว (ลงเวลาเข้างาน / กรอกเอง / นับจากบัญชีต่อไป)
- จะเปลี่ยนจาก "ณ ขณะนี้" เป็นนับตามกะของวันหรือค่าสูงสุดของวันหรือไม่
- กลุ่มอื่นที่อยู่ในศูนย์ เช่น ญาติที่มาเยี่ยมหรือเจ้าหน้าที่หน่วยงานภายนอก รอบนี้ไม่นับ

## Migration

ไม่มี — ไม่มีเอกสารที่ persist ฐานคนนี้ ค่าถูกคำนวณตอนอ่านทุกครั้ง ไม่มี `schema_v` ใดเปลี่ยน

`daily_calc.occupancy_snapshot` (CR-036/CR-042, engine คนละตัว) **ไม่อยู่ในขอบเขตของ CR นี้**
และยังคงนิยามเดิมตาม `docs/features/daily-sop-resource-calc-flow.md` DS-E3
